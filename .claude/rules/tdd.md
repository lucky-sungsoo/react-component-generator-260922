# TDD Rule

> **RIGID RULE — 상황에 맞게 변형하지 마라.** "이번만 예외"는 없다. 예외가 필요하다고 느껴지면 아래 "적용 기준"과 "변명 차단표"부터 다시 읽어라.

## 0. 우선순위

이 파일은 **기본값(fallback)** 이다. 프로젝트의 `CLAUDE.md`/`AGENTS.md`에 TDD 관련 규칙이 명시되어 있으면 **그쪽이 우선**한다. 충돌하는 규칙이 없을 때만 이 파일을 따른다.

## 1. 적용 기준

### TDD를 반드시 적용해야 하는 대상

- **비즈니스 로직** (계산, 상태 전이, 도메인 규칙)
- **API 엔드포인트 / 핸들러**
- **유틸리티 함수** (순수 함수, 데이터 변환)
- **버그 수정** (버그를 재현하는 실패 테스트 먼저 작성 → 수정)

### TDD가 불필요한 대상

- **타입 정의** (interface, type alias)
- **설정 파일** (config, env, build 설정)
- **순수 UI 컴포넌트** (로직 없이 props를 그대로 렌더링만 하는 마크업)
- **SQL / 마이그레이션 스크립트**

판단이 애매하면 "조건 분기나 계산이 있는가"로 가른다. 있으면 적용 대상이다.

## 2. RED-GREEN-REFACTOR 사이클

### RED

- **하나의 동작 = 하나의 테스트.** 여러 동작을 한 테스트에 묶지 않는다.
- 테스트를 작성한 뒤 **반드시 실행해서 실패를 눈으로 확인**한다. 실행하지 않은 테스트는 존재하지 않는 것과 같다.
- 실패 이유는 오직 **"기능 미구현"** 이어야 한다. 문법 오류, import 누락, 오타로 인한 실패는 RED가 아니라 그냥 깨진 테스트다 — 먼저 고친다.

### GREEN

- 테스트를 통과시키는 **최소한의 코드만** 작성한다.
- **YAGNI**: 지금 요구되지 않은 조건 분기, 파라미터, 확장 포인트를 미리 만들지 않는다.
- 통과 확인은 **신규 테스트 + 기존 테스트 전체**를 대상으로 한다. 기존 테스트를 건너뛰고 신규 테스트만 통과했다고 끝내지 않는다.

### REFACTOR

- 중복 제거, 이름 개선, 헬퍼 추출만 한다.
- 전체 테스트가 **green으로 유지**되는지 매 변경 후 확인한다.
- 이 단계에서 **새로운 동작을 추가하지 않는다.** 새 동작이 필요하면 다음 사이클의 RED에서 다룬다.

### 반복

REFACTOR가 끝나면 다음 동작에 대한 **RED로 돌아간다.** 사이클을 건너뛰지 않는다.

## 3. 삭제 강제 규칙

- 테스트보다 프로덕션 코드를 먼저 작성한 사실을 발견하면, **그 코드를 삭제하고 RED부터 다시 시작한다.**
- "참고용"이라며 주석 처리하거나 별도 파일로 남기는 것도 **금지**한다. 삭제는 완전한 삭제여야 한다.

## 4. 변명 차단표

| 변명 | 반론 |
|---|---|
| 너무 단순해서 테스트 불필요 | 단순한 코드일수록 테스트 작성 비용도 낮다. 비용이 낮은데 안 할 이유가 없다. 단순하다는 판단 자체가 틀렸을 때 테스트가 그것을 증명한다. |
| 나중에 추가하겠다 | 나중은 오지 않는다. RED 없이 작성된 코드는 이미 "먼저 작성한 프로덕션 코드"이므로 규칙 3에 따라 삭제 대상이다. |
| 시간이 없다 | 테스트 없이 짠 코드의 디버깅 시간이 테스트 작성 시간보다 항상 길다. 지금 아끼는 시간은 나중에 이자를 붙여 갚는다. |
| 삭제하면 낭비다 | 검증되지 않은 코드는 자산이 아니라 부채다. 실패하는 테스트로 보호되지 않는 코드는 언제든 조용히 깨질 수 있다. |
| 프로토타입이다 | 프로토타입이 프로덕션으로 승격되는 순간 테스트 없는 코드가 그대로 남는다. 지금 규칙을 적용하지 않으면 나중에 적용할 계기도 없다. |

## 5. 예외

이 파일에 없는 예외는 없다. 예외가 필요하다고 판단되면 프로젝트의 `CLAUDE.md`/`AGENTS.md`에 근거와 함께 명시적으로 기록하고, 그 문서의 우선순위를 따른다.
