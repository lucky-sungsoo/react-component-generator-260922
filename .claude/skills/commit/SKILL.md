# commit: 컨벤션 기반 커밋

변경사항을 분석해 커밋 메시지를 스스로 작성하고, 승인 절차 없이 바로 커밋한다. 무엇을 커밋할지, 메시지를 어떻게 쓸지는 사용자가 아니라 이 스킬이 판단한다.

## 절차

### Step 1: 저장소 컨벤션 확인

`git log --oneline -20`으로 최근 커밋 메시지 스타일을 확인한다. 이 저장소만의 접두어·형식이 이미 쓰이고 있으면 그것을 따르고, 없거나 판단하기 어려우면 아래 "메시지 형식"을 기본값으로 쓴다.

### Step 2: 변경사항 분석

- `git status`로 추적되지 않은 파일과 변경된 파일을 확인한다.
- `git diff`(unstaged)와 `git diff --staged`(staged)로 실제 변경 내용을 확인한다.
- 시크릿·자격증명으로 보이는 파일(`.env`, `credentials.json` 등)이 포함돼 있으면 커밋 대상에서 제외하고 사용자에게 알린다.

### Step 3: 논리적 단위로 분류

변경사항을 하나의 목적을 공유하는 단위로 묶는다:

- 서로 다른 목적(예: 기능 추가 + 무관한 버그 수정)이 섞여 있으면 여러 커밋으로 나눈다.
- 같은 목적을 위해 여러 파일이 함께 바뀐 경우(예: 컴포넌트 + 그 테스트)는 하나의 커밋으로 묶는다.
- 나눌지 합칠지 애매하면 가장 합리적인 분류를 스스로 정하고 진행한다(확인을 위해 멈추지 않는다).

파일은 `git add -A`나 `git add .`이 아니라 커밋 단위에 해당하는 파일을 이름으로 지정해 스테이징한다.

### Step 4: 커밋 메시지 작성

각 커밋 단위마다 한국어 커밋 메시지를 작성한다.

**메시지 형식** (저장소에 다른 컨벤션이 없을 때 기본값):

```
<type>: <한 줄 요약>

<필요할 때만 본문: 왜 이 변경이 필요했는지>
```

`type`은 다음 중 변경 성격에 맞는 것을 고른다:

- `feat`: 새로운 기능 추가
- `fix`: 버그 수정
- `refactor`: 동작 변화 없는 구조 개선
- `chore`: 빌드 설정, 의존성, 잡무성 변경
- `docs`: 문서만 변경
- `test`: 테스트 추가·수정
- `style`: 포맷팅 등 코드 의미에 영향 없는 변경

요약은 무엇을 했는지가 아니라 왜 했는지가 드러나도록 간결하게 쓴다(코드 diff로 알 수 있는 내용을 그대로 나열하지 않는다). 본문은 꼭 필요할 때만 붙이고 억지로 채우지 않는다.

### Step 5: 바로 커밋

승인을 구하지 않고 `git add <파일...>` → `git commit -m "..."` 순으로 바로 커밋한다. 여러 단위로 나눴다면 그 순서대로 여러 개의 커밋을 만든다. 커밋 메시지는 개행이 포함될 수 있으므로 heredoc으로 전달한다.

단, 스테이징 직전 `git status`로 포함되는 파일을 다시 한번 확인해 시크릿·자격증명 파일이나 의도치 않은 파일이 섞이지 않았는지 점검한다(승인을 구하라는 뜻이 아니라 실수 방지용 점검이다).

커밋 완료 후 `git status`와 `git log --oneline -n <커밋 수>`로 결과를 확인해 무엇을 몇 개의 커밋으로 나눠 커밋했는지 간단히 보고한다. 사용자가 명시적으로 요청하지 않으면 push하지 않는다.

## 하지 않는 것

- `--no-verify`, `--no-gpg-sign` 등 훅·서명 우회 플래그를 사용하지 않는다.
- 기존 커밋을 `--amend`로 수정하지 않는다(사용자가 명시적으로 요청한 경우만 예외).
- 시크릿·자격증명으로 보이는 파일은 승인 없이도 절대 커밋하지 않고, 발견 시 커밋을 중단하고 사용자에게 알린다.
- 변경사항이 없으면 빈 커밋을 만들지 않고 그 사실을 알린다.
- 사용자가 명시적으로 요청하지 않으면 push하지 않는다.
